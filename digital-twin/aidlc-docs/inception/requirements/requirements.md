# 要件定義書: digital-twin

**プロジェクト**: ShadowSync - digital-twin  
**バージョン**: 1.0  
**日付**: 2026-05-10  
**ステータス**: 承認済み

---

## 1. 意図分析サマリー

### 1.1 ユーザーリクエスト
ShadowSyncのdigital-twinとして、蓄積済みの個人活動ログを検索し、ユーザーの自然言語質問に回答する対話型アプリケーションを構築する。今回の依頼範囲はinceptionフェーズのみであり、constructionフェーズの実装・詳細設計・テスト作成は開始しない。

### 1.2 リクエストタイプ
**新規プロジェクト** - Greenfieldのデスクトップ対話アプリケーションおよびAWSバックエンド連携システム。

### 1.3 スコープ見積もり
**システム全体** - 以下を含む。
- デスクトップUI
- ユーザー認証
- Conversation API
- RAG検索連携
- LLM回答生成
- 回答根拠表示
- 会話履歴保存
- マルチテナント分離

### 1.4 複雑度見積もり
**複雑** - 以下の理由による。
- ローカルデスクトップアプリとAWSバックエンドの境界設計が必要
- data-accumulationが構築するS3 Vectorsベースのユーザー別ナレッジベースと統合する
- 回答生成、検索根拠、会話履歴を分離して扱う必要がある
- `user_id` によるマルチテナント分離をアプリケーション層、IAM、ストレージ設計で担保する
- Security BaselineとProperty-Based Testing拡張ルールを有効化する

---

## 2. 前提と依存関係

### 2.1 システム前提
- data-accumulationが、活動ログの収集、正規化、蓄積、ベクトル化を担う。
- digital-twinは、データの収集、蓄積、パース処理を行わない。
- digital-twinは、蓄積済み活動ログを検索し、回答生成と対話体験を提供する。

### 2.2 外部依存
- **認証**: Amazon Cognito User Pool
- **RAG検索**: data-accumulationが作成するS3 Vectorsベースのユーザー別ナレッジベース
- **回答生成LLM**: Amazon Bedrock上のNova系モデル
- **活動ログストア**: data-accumulation側で管理されるため、digital-twinは読み取り連携を前提とする

## 3. 機能要件

### FR-1: デスクトップ対話UI
- digital-twinはデスクトップアプリケーションとして提供する。
- ユーザーはテキスト入力で質問できる。
- アプリは回答本文、参照元、根拠情報を表示できる。
- 会話履歴を閲覧できる。
- 認証状態、応答中状態、エラー状態をユーザーに分かる形で表示する。

### FR-2: ユーザー認証
- Amazon Cognito User Poolを利用してユーザー認証を行う。
- バックエンドは認証トークンを検証し、信頼できる `user_id` をサーバー側で確定する。
- クライアントから送信された `user_id` は信頼しない。
- すべてのユーザー固有データアクセスは、認証トークン由来の `user_id` に基づいて実行する。

### FR-3: 質問受付とConversation API
- デスクトップアプリは、ユーザー質問をConversation APIへ送信する。
- Conversation APIは入力を検証し、質問本文、会話セッション、認証済み `user_id` を扱う。
- APIは検索、回答生成、会話履歴保存をオーケストレーションする。
- 長文入力、空入力、不正形式、認証切れ、検索失敗、LLM失敗を扱う。

### FR-4: RAG検索連携
- ユーザー質問をもとに、data-accumulationが作成するS3 Vectorsベースのユーザー別ナレッジベースを検索する。
- 検索時には必ず認証済み `user_id` による分離条件を適用する。
- 検索結果には、回答生成に必要な本文、時刻、ソース種別、参照元識別子、スコアを含める。
- 他ユーザーの活動ログを検索結果に混入させてはならない。

### FR-5: 回答生成
- Amazon Bedrock上のNova系モデルを利用して回答を生成する。
- 回答生成プロンプトには、ユーザー質問、直近会話文脈、RAG検索結果を含める。
- 活動ログ由来の根拠と会話履歴由来の文脈を区別して扱う。
- 回答は日本語を主対象とする。
- 初期応答時間の許容目標は10秒以内とする。

### FR-6: 回答根拠表示
- 回答には参照元または根拠を必ず表示する。
- 根拠は、活動ログの時刻、ソース種別、関連抜粋、参照元識別子を含む。
- 回答内で、活動ログに基づく事実と推論を区別できるようにする。
- 根拠が不足している場合は、断定を避け、不足している情報を明示する。

### FR-7: 会話履歴保存
- 会話履歴は永続保存する。
- 会話履歴は検索対象の活動ログとは分離して保存する。
- 会話履歴は後続質問の文脈として利用できる。
- 会話履歴は、ユーザー別、セッション別に取得できる。
- 会話履歴には、ユーザー質問、生成回答、参照元、生成時刻、モデル情報、処理結果を含める。

### FR-8: マルチテナント分離
- `user_id` による分離をアプリケーション層、IAM、ストレージ設計で担保する。
- RAG検索、会話履歴、監査ログ、設定情報のすべてでユーザー境界を維持する。
- アプリケーション層では、全リクエストで認証済み `user_id` に基づく認可を行う。
- ストレージ設計では、ユーザー別パーティション、prefix、namespaceなどにより境界を明示する。
- IAMでは、可能な範囲でユーザー別リソースまたはprefixへのアクセス制限を行う。

### FR-9: 監査とトレーサビリティ
- APIリクエスト、検索実行、回答生成、認可失敗、エラーを監査できる。
- 監査ログには、ユーザー識別子、時刻、リクエストID、処理結果、エラー分類を含める。
- 機微情報、認証トークン、全文プロンプトなどを不用意にログ出力してはならない。

## 4. 非機能要件

### NFR-1: セキュリティ
- Security Baseline拡張ルールをブロッキング制約として適用する。
- 保存データは暗号化する。
- 通信はTLS 1.2以上を前提とする。
- API入力は型、長さ、形式、サイズを検証する。
- CORSは認証済みエンドポイントでワイルドカードを使用しない。
- 認証・認可ロジックは専用コンポーネントに集約する。
- 最小権限IAMを適用し、ワイルドカード権限は原則禁止する。
- セキュリティイベントのログとアラートを設計対象に含める。

### NFR-2: プライバシー
- 活動ログと会話履歴は高機微データとして扱う。
- 他ユーザーのデータが回答、根拠、履歴に混ざらないことを最重要制約とする。
- ログ出力に質問全文、回答全文、検索結果全文を残す場合は、保持期間とアクセス制御を明示する。

### NFR-3: パフォーマンス
- 初期目標として、通常質問の応答完了は10秒以内を許容範囲とする。
- 検索、プロンプト構築、LLM呼び出し、履歴保存の各処理時間を計測可能にする。
- 将来のストリーミング応答導入を妨げないAPI境界とする。

### NFR-4: 信頼性
- RAG検索失敗、LLM呼び出し失敗、会話履歴保存失敗を区別して扱う。
- 一部処理に失敗した場合でも、ユーザーに原因と再試行可能性を示す。
- 外部依存サービスのタイムアウトとリトライ方針を設計する。

### NFR-5: テスト容易性
- Property-Based Testing拡張ルールを有効化する。
- 検索条件構築、`user_id` フィルタ適用、プロンプト構築、入出力シリアライズ、履歴保存モデルをPBT対象候補とする。
- 重要なユーザーシナリオは例示ベーステストでも検証する。

### NFR-6: 保守性
- UI、認証、Conversation API、RAG検索、回答生成、会話履歴、監査を責務分離する。
- data-accumulationとの結合点は明確なインターフェースで隠蔽する。
- LLMモデルや検索バックエンドの差し替えに備え、実装依存を局所化する。

## 6. Inception実行方針

ユーザー回答により、inception内では以下を実行する。

- 要件分析: 実行
- ユーザーストーリー: 実行
- ワークフロー計画: 実行
- アプリケーション設計: 実行
- 作業単位計画: 実行
- 作業単位生成: 実行

Constructionフェーズは今回開始しない。

## 7. リスクと未確定事項

### 7.1 主なリスク
- S3 Vectorsベースの検索API・メタデータフィルタ仕様により、設計の詳細が変わる可能性がある。
- Nova系モデルの回答品質が期待に満たない場合、Claude系モデルへの切り替え判断が必要になる。
- デスクトップアプリの認証フローは、Cognito連携方式によってUXと実装難度が変わる。
- 回答根拠を必ず表示するため、検索結果のメタデータ品質が回答品質に直結する。
- `user_id` 分離はセキュリティ上の最重要制約であり、後工程で設計・テストの重点対象にする必要がある。

### 7.2 後続ステージで詳細化する事項
- デスクトップアプリ技術選定
- 認証フロー詳細
- Conversation APIのエンドポイント設計
- RAG検索インターフェース
- プロンプト構築方式
- 会話履歴スキーマ
- 監査ログ保持期間
- PBT対象プロパティ

## 8. 拡張ルール適用状況

| 拡張ルール | 有効化 | 要件分析での扱い |
|---|---|---|
| Security Baseline | はい | セキュリティ要件として反映済み |
| Property-Based Testing | はい | テスト容易性・後続設計制約として反映済み |

### 適合サマリー
- Security Baseline: 要件レベルでは適合。詳細な検証はアプリケーション設計、非機能設計、インフラ設計、コード生成で継続する。
- Property-Based Testing: 要件レベルでは適合。具体的なプロパティ識別は機能設計以降で実施する。
